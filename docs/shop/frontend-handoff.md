# Frontend Saliy Studio: актуальный handoff

Состояние на **8 ноября 2026**, Екатеринбург (UTC+5). Документ объединяет
контракт витрины Next.js и админки Vite. [Изменения за сегодня](../changes-2026-11-08.md)
содержат список обновлений и патчи для frontend.

## Адреса и авторизация

| Назначение | Адрес |
| --- | --- |
| Магазин | `https://saliystudio.com` |
| Админка | `https://admin.saliystudio.com` |
| Браузерный API | `/api`, на домене текущего приложения |
| SSR магазина | `API_URL=http://127.0.0.1:3000/api` |

В новых метаданных, sitemap, ссылках и настройках использовать новый домен.
Все маршруты ниже включают `/api` — не добавлять префикс дважды.

Покупатель входит через Better Auth: отправка кода и вход —
`POST /api/session/email-otp/send-verification-otp` (`{ email, type: 'sign-in' }`)
и `POST /api/session/sign-in/email-otp` (`{ email, otp }`).
Сессия: `GET /api/session/get-session`, гостевой ответ может быть `null`.
Выход: `POST /api/session/sign-out`. Профиль: `GET /api/auth/me`.
Запросы отправлять с `credentials: 'include'`; JWT покупателя, ручного refresh
и заголовка Bearer нет. [Полный контракт](better-auth.md).

Админский вход — отдельный существующий flow `/api/admin/auth/*` с cookie
`adminToken`. Не подменять его сессией покупателя.

## Актуальная и старая цена

В товар добавлено `oldPrice: number | null`; в типах клиента допускается
`oldPrice?: number | null`, чтобы обработать отсутствие поля в старом кеше.

```ts
type ProductPrice = {
  price: number
  oldPrice?: number | null
  discount: number
}

function displayPrice(product: ProductPrice) {
  const current = product.discount > 0
    ? Math.floor(product.price * (1 - product.discount / 100))
    : product.price
  const previous = product.oldPrice
    ?? (product.discount > 0 ? product.price : null)
  return { current, previous: previous != null && previous > current ? previous : null }
}
```

Новая пара: `price` — актуальная цена, `oldPrice` — старая для отображения,
`discount: 0`. Существующая схема `price` + процентный `discount` продолжает
работать для товаров без `oldPrice`. Не применять скидку второй раз.

| Где | Что показывать |
| --- | --- |
| Каталог и карточка | Актуальную цену, рядом зачёркнутую старую, если она задана |
| Корзина и checkout | `finalPrice` и `totalPrice` из `/api/cart/validate`; `oldPrice` только для отображения |
| Итог заказа | Значения `/api/orders/calculate` и сохранённого заказа |

Не проверять цену по truthiness: `0` — число. Отсутствие старой цены — `null`
или отсутствие поля. Старую цену не включать в сумму заказа и банковский платёж.
Backend сохраняет прежнее правило расчёта скидочной цены с `Math.floor`;
не менять формат денег или правила округления отдельно во frontend.

### Формы админки

Маршруты: `POST /api/admin/products` (multipart) и
`PATCH /api/admin/products/:id` (JSON либо существующий multipart).
Пример обновления:

```json
{
  "price": 7000,
  "oldPrice": 10000,
  "discount": 0
}
```

Результат: **7 000 ₽** рядом с зачёркнутыми **10 000 ₽**; покупка по 7 000 ₽.
Для удаления старой цены отправить `{ "oldPrice": null }`; отсутствие поля
при PATCH сохраняет прежнее значение. При создании без старой цены не добавлять
это поле в FormData. Числа в multipart передавать строками.

Старая цена должна быть больше актуальной. `oldPrice` вместе с ненулевым
`discount` отклоняется HTTP 400. В форме проверить условия до любых запросов
загрузки/удаления фото и показать сообщение пользователю.

При открытии прежнего товара со скидкой форма показывает рассчитанную цену
в актуальной, исходную `price` — в старой. При сохранении отправляет новую пару
и `discount: 0`. [Подробный API админки](../Admin/products.md).

## Размер OS

`OS` — **One Size**, единый размер. Код в API строго `OS`, а не `ONE SIZE`,
`OS_SIZE` или `os`. Админка предлагает `XS`, `S`, `M`, `L`, `XL`, `OS`.
Пример остатков: `{ "OS": 12 }`.

Витрина строит размеры из ключей `stock`; не ограничивать их фиксированным
списком XS–XL. Передавать выбранный ключ без переименования в корзину и заказ:
`{ productId, size: 'OS', quantity }`. Остаток задаёт менеджер; существующим
товарам OS автоматически не добавлялся.

### Откуда витрина получает OS

Цепочка данных: **менеджер выбирает OS и задаёт остаток в админке →
админка сохраняет `stock` товара через API → backend хранит этот JSON в БД →
витрина получает `stock` вместе с товаром**.

| Запрос витрины | Где читать размеры |
| --- | --- |
| `GET /api/products` | `response.products[i].stock` |
| `GET /api/products/:slug` | `response.stock` (товар возвращается без обёртки) |

Например, фрагмент ответа карточки товара:

```json
{
  "id": 123,
  "slug": "example-product",
  "stock": { "OS": 12 }
}
```

Здесь фронт показывает размер `OS` («Единый размер») и получает остаток `12`.
Отдельного запроса для получения справочника размеров или признака `isOneSize`
нет: источник размера — ключ в объекте остатков конкретного товара.

```ts
const sizes = Object.entries(product.stock ?? {}).map(([size, quantity]) => ({
  value: size, // В корзину и заказ уходит именно этот код, например OS.
  label: size === 'OS' ? 'Единый размер' : size,
  quantity,
  disabled: quantity <= 0,
}))
```

Для `cardStatus === 'PRE_ORDER'` всё так же: размеры и количество берутся из
обычного `stock` — у предзаказа это сколько можно предзаказать
([контракт предзаказов](preorders.md)). Поля `preorderStock` больше нет.
`stock: { "OS": 0 }` означает существующий размер без физического остатка;
если ключа `OS` нет, добавлять его на витрине автоматически не нужно.
Если OS не появился после сохранения, проверить `stock` в свежем ответе API,
обновление кеша товара и отсутствие фильтра размеров по фиксированному XS–XL.

## Фото в админке

Количество выбранных фото не ограничено на уровне формы. Сервер сохраняет
лимит **до 10 файлов в одном запросе**, каждый **до 10 МиБ**, JPG/JPEG, PNG, WebP.
Имя multipart-поля — **`images`**, повторяемое для каждого файла, без `[]` в имени.
На уровне Nginx весь запрос ограничен 25 МБ.

| Операция | Текущая отправка |
| --- | --- |
| Создание товара | Данные и первые два фото в `POST /api/admin/products`, следующие по два через маршрут добавления |
| Добавление к товару | Последовательно по одному фото: `POST /api/admin/products/:id/images` |
| Порядок/превью | Сначала сохранить изменения существующей галереи, затем добавлять новые фото |

Ответ добавления: `{ message, product }`; брать обновлённые изображения из
`product.images`. Сохранять порядок файлов, не отправлять партии параллельно:
backend дописывает массив изображений товара.

- Проверить формат/размер всех выбранных файлов до первого запроса.
- После подтверждённой партии исключить её из очереди повторной отправки.
- Показывать `Фото N/M` — число подтверждённых файлов, не процент байтов.
- Multipart-запрос: таймаут 120 секунд с учётом чтения ответа. Сохранение полей,
  порядка и удаления фото: 30 секунд.
- При потере ответа не считать файл гарантированно несохранённым. Перечитать
  товар перед повтором: серверной идемпотентности загрузки нет.
- Если товар создан, а следующие фото не загрузились, открыть созданную
  карточку с сообщением об оставшихся фото; не создавать товар повторно.

По уточнению владельца, менеджер смог загрузить фото с телефона, но передача
занимает много времени. Пока идёт загрузка, сохранять счётчик и блокировать
повторное сохранение; не показывать успех до ответа сервера.
[Форматы изображений на витрине](images.md).

## СДЭК, checkout и оплата

Новая рабочая учётка СДЭК включена; секреты хранятся только на backend.
Браузер вызывает существующие `/api/delivery/cities`,
`/api/delivery/pickup-points`, `/api/delivery/prices`.
Для поиска города передать `countryCode` и `search` либо `regionCode`;
для ПВЗ — `cityCode`. [Контракт доставки](delivery.md).

Стоимость доставки получать из API для выбранного маршрута и состава заказа;
не зашивать её в интерфейс. Смена учётной записи СДЭК не меняет публичные
маршруты и тела запросов frontend.

Новый заказ: только `CARD_ONLINE`, подпись «Т-Банк». Получать `paymentUrl`
из создания заказа, после банка читать `GET /api/orders/:orderNumber`.
Оплачено только по серверному состоянию; одна страница успеха ничего не подтверждает.
[Handoff оплаты](tbank-frontend-handoff.md).

## Предзаказы

Backend-контракт предзаказов доступен отдельно: [preorders.md](preorders.md).
Состояния `PRE_ORDER`, `AWAITING_PREORDER`, признаки `isPreorder`/`preorderReady`
нельзя сводить к обычному наличию/отправке. Поля, тексты перед оплатой и
обработка статусов описаны в указанном контракте.

## Передача в репозитории frontend

Витрина и админка — отдельные приложения; в этом backend-репозитории находятся
документация и патчи. Порядок патчей указан в
[отчёте за сегодня](../changes-2026-11-08.md). Перед переносом использовать
`git apply --check`, сопоставить с текущими исходниками и не применять повторно
уже перенесённые изменения. В серверной сборке они уже опубликованы.

После получения новой версии менеджер должен обновить страницу админки.
