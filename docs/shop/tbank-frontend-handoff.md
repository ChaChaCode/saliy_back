# Переход frontend Saliy на Т-Банк

Дата: 31 октября 2026. Документ основан на исходниках frontend на сервере
(`/home/deploy/apps/saliy_front`, коммит `cf9ea26`) и текущих локальных изменениях backend.

## 1. Состояние интеграции

Нужно заменить выбор Точки/Яндекс Сплита на оплату через Т-Банк и сохранить маршрут
возврата с проверкой фактической оплаты. Значение метода в API — `CARD_ONLINE`.

**Новый backend пока не включён в рабочем магазине.** Подготовленная версия находится
в `/home/deploy/releases/backend-20261031-tbank-v1`. Рабочий API пока предлагает
`SBP_TOCHKA` и `YANDEX_PAY`. Не выкладывать checkout с одним `CARD_ONLINE`
отдельно от переключения backend.

Проверен отдельный платёж DEMO-терминала: банк вернул `CONFIRMED` для суммы 1 ₽.
Это не проверка полного оформления: тест создавался без заказа в БД,
без явно переданного адреса возврата и без проверки обновления заказа по webhook.
Для реальных оплат нужны боевые настройки; сейчас есть только тестовый терминал.

## 2. Контракт API новой версии

Все адреса ниже включают `/api`. Если общий API-клиент уже добавляет этот префикс,
в сервисах оставлять `/orders/...` без второго `/api`.

| Запрос | Что использовать на frontend |
| --- | --- |
| `GET /api/orders/delivery-options?country=RU` | `paymentMethods: ["CARD_ONLINE"]`; доставка для RU/BY: `CDEK_PICKUP`, `STANDARD` |
| `POST /api/orders/calculate` | Существующее тело расчёта, но `paymentMethod: "CARD_ONLINE"`; цены и итог брать из ответа |
| `POST /api/orders` | Существующие товары, контакты и доставка, но `paymentMethod: "CARD_ONLINE"` |
| `GET /api/orders/:orderNumber` | Состояние заказа: прежде всего `isPaid` и `status`; может вернуть JSON `null` для неизвестного номера |

Фрагмент ответа создания заказа (остальные существующие поля сохраняются):

```json
{
  "orderNumber": "<номер заказа из API>",
  "paymentMethod": "CARD_ONLINE",
  "status": "PENDING",
  "isPaid": false,
  "paymentUrl": "https://pay.tbank-online.com/<идентификатор>"
}
```

`orderNumber` — номер заказа магазина; его использовать в `/order/...`.
Банковский `PaymentId` и внутренний `id` заказа для этого маршрута не подходят.
Ссылку брать только из ответа создания заказа, самостоятельно не собирать.

Новая версия отклоняет остальные методы оплаты HTTP 400. При ошибке инициализации
платежа также возвращается HTTP 400 с сообщением
`Не удалось инициализировать платёж. Попробуйте позже.`

**Публичного `POST /api/payment/tbank/check-status` сейчас нет.** Не вызывать и не
закладывать его в реализацию. Backend получает подтверждения через webhook
и дополнительно опрашивает незавершённые платежи раз в минуту.
Браузер только читает заказ через `GET /api/orders/:orderNumber`.

## 4. Переход на форму банка

В `CheckoutContainer.tsx` сейчас есть две проблемы:

1. `clearCart()`, `clearPersonal()`, `clearDelivery()` и удаление query-кэша выполняются
   сразу после создания заказа, до подтверждения оплаты и даже до проверки URL.
2. При отсутствии `paymentUrl` выполняется переход сразу на `/success`.

Для нового онлайн-flow:

1. Заблокировать повторный submit на время запроса создания заказа.
2. Получить `orderNumber` и непустой `paymentUrl`.
3. Проверить адрес. Разрешать HTTPS и точное доверенное имя хоста, не проверку
   через `includes('tbank')`. Проверить, что URL не содержит логин/пароль.
4. Выполнить `window.location.assign(paymentUrl)`.
5. Если ссылки нет либо она не прошла проверку — показать ошибку и сохранить корзину.
   Успех в этом случае не показывать. Не создавать новый заказ автоматически в цикле.
6. Сбрасывать корзину и обновлять её серверный кэш после подтверждённой оплаты,
   согласовав поведение для гостя и авторизованного покупателя.

Минимальная проверка URL для **нового Т-Банк flow**:

```ts
function isAllowedTbankPaymentUrl(value: string): boolean {
  try {
    const url = new URL(value)
    return url.protocol === 'https:' &&
      url.hostname === 'pay.tbank-online.com' &&
      (url.port === '' || url.port === '443') &&
      url.username === '' && url.password === ''
  } catch {
    return false
  }
}
```

Домен подтверждён реально полученной ссылкой DEMO-платежа. Другие домены добавлять
только после проверки реального ответа банка/документации. При сохранении старого
flow не ломать его отдельный список банковских адресов до согласованного отключения.

## 5. Возврат после оплаты

Backend уже формирует адреса:

```text
Успех:  https://saliyclothes.com/order/{orderNumber}?payment=success
Ошибка: https://saliyclothes.com/order/{orderNumber}?payment=fail
```

Frontend не передаёт эти URL в запрос создания заказа: backend получает базовый
адрес из `FRONTEND_URL` и отправляет `SuccessURL`/`FailURL` банку при Init.

Страница `/order/[id]` должна прочитать заказ и выбрать результат:

| Состояние API | Экран |
| --- | --- |
| `isPaid === true` | `/order/{orderNumber}/success` |
| `status === 'CANCELLED'` или `'PAYMENT_FAILED'`, не оплачен | `/order/{orderNumber}/failed` |
| `status === 'REFUNDED'` | Сообщение о возврате; не «оплата обрабатывается» |
| `PENDING`, `isPaid === false` | Продолжить ограниченный polling, затем `/pending` |
| JSON `null` или HTTP 404 | «Заказ не найден» или согласованный переход в магазин |
| Ошибка сети / 5xx | Сообщение и повторная проверка; не объявлять оплату неуспешной только из-за сети |

`payment=success` — подсказка о возврате, не доказательство оплаты.
При `payment=fail` тоже сначала сверять заказ: подтверждённая оплата имеет приоритет
над query-параметром. Пользователь может открыть URL вручную или вернуться на старый адрес.

Текущие 8 опросов с интервалом 4 секунды могут закончиться раньше минутного
backend polling. Рекомендуемый бюджет ожидания 90–120 секунд с интервалом 4–5 секунд,
после чего оставить понятный pending-экран с возможностью повторить проверку.
Не выполнять параллельные бесконечные запросы; отменять таймеры/запросы при уходе со страницы.
Обновление pending-страницы и повторное открытие результата должны работать.

Не определять оплату по наличию `paymentUrl`, возврату браузера или одному лишь
статусу заказа `CONFIRMED`: основной сигнал UI — `isPaid`, установленный backend.
Не создавать заказ повторно со страницы результата.

## 6. Страница успеха и гостевой заказ

Сейчас success-страница загружает заказ и рисует «Спасибо за заказ» без проверки
`isPaid`. Нужно проверять оплату и при прямом открытии `/success`.

Для гостя и чужого пользователя backend возвращает персональные поля `null`, в том
числе `firstName`, `lastName`, `email`, `phone`, адрес. Не выводить «null, спасибо»
или пустой email. Использовать нейтральное «Спасибо за заказ!» и номер заказа.
Тип ответа чтения заказа должен учитывать `null` и nullable-персональные поля.
Для своего заказа сохранять существующую передачу авторизационных cookies.

Текущий текст обещает, что трек-код уже отправлен на почту сразу после оплаты.
Заменить на сообщение об успешной оплате/оформлении; трек-код показывать и обещать
его отправку только при соответствующем подтверждённом состоянии доставки.

## 7. Что остаётся на backend

- Реквизиты терминала, подпись Token, Init/GetState и вызовы банка.
- Приём `POST /api/payment/tbank/webhook`, проверка подписи, суммы, OrderId и PaymentId.
- Подтверждение `isPaid`, обновление заказа, серверная корзина и дальнейшая обработка.
- Адреса возврата, настройка доступного способа оплаты и переходный период старых платежей.

Не размещать пароль терминала в `NEXT_PUBLIC_*`, исходниках браузера или localStorage.
Frontend не должен вызывать банковский API с секретами или имитировать webhook.

Есть backend-вопрос до полного теста: первый отдельный Init с дополнительными
параметрами вернул ошибку 9999, минимальный Init был успешен. Причина не установлена.
Штатный `registerOrder` передаёт `PayType`, `RedirectDueDate` и URL; его нужно проверить
целиком с настройками терминала. Фискализация Receipt пока не реализована.

## 8. Приёмочные сценарии

- Гость и авторизованный пользователь: в новой форме выбран Т-Банк, в запросах
  расчёта и создания `CARD_ONLINE`; старое сохранённое значение корректно мигрирует.
- Адрес `pay.tbank-online.com` принимается; HTTP, посторонний хост и похожий домен отклоняются.
- Двойной клик не порождает параллельные заказы; ошибка API/отсутствие ссылки сохраняет корзину.
- Успешная тестовая карта: создание настоящего тестового заказа, форма банка,
  возврат на `/order/{orderNumber}?payment=success`, подтверждение `isPaid`, экран успеха.
- Отклонённая карта/отмена: корректный failed или pending по состоянию API, корзина сохранена.
- Задержанный webhook, временная ошибка сети и fallback polling: нет преждевременного успеха/отказа.
- Прямое открытие `/success` неоплаченного заказа не показывает успех.
- Неизвестный номер и JSON `null` обработаны без падения.
- Гостевая success-страница работает при `firstName/email === null`.
- Старая история заказов Точки/Яндекса читается, названия отображаются корректно.
- В новых сценариях браузер не вызывает `/payment/alfa/check-status`,
  `/payment/yandex/check-status` или несуществующий `/payment/tbank/check-status`.

Весь flow проверить в согласованной тестовой среде с тестовыми картами Т-Банка.
Переключение рабочего checkout, backend и настроек терминала выполнять совместно.
