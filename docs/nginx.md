# Nginx: продакшн-конфигурация фронта, API и SPA-админки

Универсальная методика для VPS с nginx, где за одним доменом живут:
фронт на Node (SSR), API на Node, админка (статическая SPA или отдельный
Node-процесс). Плейсхолдеры в угловых скобках заменяются под конкретный
проект.

Снимок фактического прод-конфига проекта держите в `deploy/nginx/` рядом
с этой докой (см. Принципы п.10) — вместе с примечаниями, что применено
и какие зазоры остались.

## Что такое nginx (база)

Nginx — это **обратный прокси и веб-сервер**: первая программа, в которую
попадает каждый запрос из интернета, прежде чем дойти до вашего кода.

Обязанности в типовой схеме «nginx перед Node»:

| Задача | Почему nginx, а не Node |
|---|---|
| **TLS (HTTPS)** | терминирует шифрование; Node общается с ним по нешифрованному localhost |
| **Маршрутизация** | `/api` → бэкенд:3002, `/` → фронт:3000, `admin.` → админка — по правилам `server`/`location` |
| **Статика с диска** | отдаёт файлы на порядок дешевле, чем Node-процесс |
| **Сжатие (gzip)** | жмёт ответы перед отправкой клиенту |
| **Буферизация и лимиты** | медленные клиенты, ограничение размера тела, rate-limit |
| **Отказоустойчивость** | maintenance-страница, пока Node перезапускается |

Устройство: master-процесс читает конфиг и управляет, worker-процессы
(обычно по числу ядер) обслуживают соединения через event loop — поэтому
nginx держит тысячи соединений с копеечной памятью.

Ключевые команды: `nginx -t` — проверить синтаксис конфига (обязательно
перед применением), `systemctl reload nginx` — применить без разрыва
соединений (master перечитывает конфиг, воркеры сменяются плавно).

## Плейсхолдеры

| Плейсхолдер | Что это | Пример |
|---|---|---|
| `<DOMAIN>` | основной домен | example.com |
| `<ADMIN_DOMAIN>` | домен админки | admin.example.com |
| `<API_PORT>` | порт бэкенда (Node) | 3000 |
| `<FRONT_PORT>` | порт фронта (Node SSR) | 3001 |
| `<FRONT_STATIC>` | путь к статике сборки фронта | /home/deploy/apps/\<app\>/.next/static |
| `<ADMIN_ROOT>` | root SPA-админки (если статическая) | /home/deploy/apps/\<admin\>/dist |
| `<ADMIN_PORT>` | порт админки (если это Node-процесс) | 3002 |

Порт бэкенда — это то, что реально слушает процесс на сервере (проверять по
pm2/`.env` на сервере, а не по локальному .env: значения могут расходиться).
Конфиг nginx обязан совпадать с фактическим портом процесса.

## Принципы

1. **Nginx отдаёт статику с диска, Node только рендерит.** Иммутабельные
   ассеты сборки (хэш в имени) отдаём напрямую с диска, минуя Node-процесс —
   быстрее и разгружает SSR.
2. **Сжатие обязательно.** Стоковый nginx сжимает только HTML (`gzip_types`
   закомментирован). JS/CSS/JSON без сжатия через дросселируемые каналы
   (РФ-провайдеры) грузятся медленно — включаем сжатие явно.
   **woff2 в `gzip_types` НЕ включать**: формат внутри уже сжат Brotli,
   гзип его не уменьшает, только жжёт CPU. Гзип осмыслен лишь для
   устаревших ttf/otf/eot.
3. **HTTP/2 — способом под версию nginx.** Один мультиплексированный
   коннект вместо шести параллельных HTTP/1.1. В nginx **1.25.1+**
   включается директивой `http2 on;`, в **1.24 и ранее** — суффиксом в
   listen: `listen 443 ssl http2;` (директива `http2 on;` на старых даёт
   ошибку "unknown directive"). Проверять версию: `nginx -v`.
4. **Keepalive к upstream — только через `upstream`-блок.** Полный
   комплект: `upstream api { server 127.0.0.1:<API_PORT>; keepalive 32; }`
   **+** `proxy_http_version 1.1` **+** `proxy_set_header Connection ""`.
   Все три части обязательны: без `upstream { keepalive N; }` две
   proxy-строки НЕ дают переиспользования соединений — nginx всё равно
   открывает новое TCP к Node на каждый запрос.
5. **Connection через map, а не наглухо.** `proxy_set_header Connection`
   для websocket требует `upgrade`, для обычных запросов — пустую строку
   (иначе ломается keepalive). Управляется
   `map $http_upgrade $connection_upgrade { default upgrade; '' ''; }`.
6. **Security-заголовки — один источник на заголовок, и сначала проверить,
   кто его уже ставит.** Современные фреймворки (Next и т.п.) часто ставят
   HSTS/X-Frame-Options/nosniff сами — проверить прямым запросом к
   Node-процессу: `curl -sI http://localhost:<PORT>/`. Если ставит
   приложение — в nginx НЕ дублировать (дубли с разными значениями, напр.
   `SAMEORIGIN` из nginx поверх `DENY` из приложения, браузеры трактуют
   непредсказуемо). Если не ставит — тогда в nginx. Для API — всегда
   бэкенд (helmet). За nginx в любом случае остаётся статика с диска —
   туда приложение заголовок добавить не может.
7. **Бэкенд за прокси — trust proxy.** Node должен доверять `X-Forwarded-*`
   только от локального nginx (`loopback`), иначе неверно вычисляет
   HTTPS/IP, а внешний клиент может подделать IP (обход rate-limit).
8. **Rate-limit на API в nginx — грубый внешний слой** поверх тонкого
   лимита в приложении (throttler). Не замена, а первая линия против
   флуда. Обязательно `limit_req_status 429;` — дефолтный 503 клиент и
   мониторинг читают как «сервер упал», а не «слишком часто».
9. **Лимит тела запроса.** Дефолт `client_max_body_size` — **1 МБ**:
   любая загрузка фото упрётся в `413 Request Entity Too Large`. Ставить
   осознанный лимит (например `100M`) в блоках, где есть аплоады.
10. **Конфиг — в git.** `/etc/nginx/` не версионируется само по себе; при
    переустановке сервера конфиг теряется. Держать снимок в репозитории
    (см. `deploy/nginx/`) и обновлять при правках. Источник истины —
    сервер, снимок — страховка.

## 1. Глобальный http-блок

Внутри `http { }` в `/etc/nginx/nginx.conf` (или отдельным файлом
`/etc/nginx/conf.d/00-tuning.conf`, он подключается автоматически):

- `gzip_vary on` + `gzip_types` со списком JS/CSS/JSON/SVG (HTML жмётся
  всегда — в список не включать; woff2 — тоже не включать, см. Принципы
  п.2). Сам `gzip on` в стоковом nginx.conf Ubuntu уже есть — не
  дублировать;
- `map $http_upgrade $connection_upgrade { default upgrade; '' ''; }`;
- `upstream` для API и фронта с `keepalive 32` (см. Принципы п.4);
- `limit_req_zone $binary_remote_addr zone=<zone>:10m rate=30r/s` +
  `limit_req_status 429;`;
- `server_tokens off` (не раскрывать версию nginx в заголовке `Server` и
  на страницах ошибок).

## 2. Основной домен (фронт + API)

`server` на 443 с SSL-строками от certbot и HTTP/2 (способ по версии — см.
Принципы п.3). Если у домена есть AAAA-запись — добавить
`listen [::]:443 ssl;` для IPv6 (без AAAA-записи не обязательно). Внутри:

- **`client_max_body_size`** под реальные аплоады (см. Принципы п.9).
- **Security-заголовки** — только те, которых не ставит само приложение
  (сначала проверить: Принципы п.6). Через `add_header ... always`.
- **`location <FRONT_STATIC-префикс>/`** → `alias <FRONT_STATIC>/` с
  `add_header Cache-Control "public, max-age=31536000, immutable"`
  (max-age обязателен: `immutable` — модификатор срока, без max-age ему
  нечего модифицировать), `add_header X-Content-Type-Options nosniff always`,
  `access_log off`. Завершающие слэши в `location` и `alias` должны
  совпадать оба.
- **`location /api/`** → `proxy_pass` на upstream API, `Connection ""`
  (keepalive), проброс `Host`/`X-Real-IP`/`X-Forwarded-For`/`X-Forwarded-Proto`,
  `limit_req zone=<zone> burst=60 nodelay`.
- **`location /`** → `proxy_pass` на upstream фронта, `Connection
  $connection_upgrade` (keepalive + websocket), проброс тех же заголовков.

Отдельный `server` на `80` — редирект `301` на HTTPS.

## 3. Домен админки

**Вариант A — статическая SPA** (`root <ADMIN_ROOT>`):

- **Security-заголовки** (для админки X-Frame-Options: DENY — не встраивать
  в iframe).
- **`location <ADMIN_ASSETS>`** — иммутабельные ассеты, кэш на год.
- **`location /`** → `try_files $uri $uri/ /index.html` (SPA-fallback);
  `index.html` НЕ кэшировать (`no-cache`), иначе новый деплой не
  подхватится. Security-заголовки в этом location продублировать.

**Вариант B — отдельный Node-процесс**: обычный `proxy_pass` на
`<ADMIN_PORT>` + тот же `/api`-location, что на основном домене. Сжатие и
keepalive нужны и здесь — блок админки легко забыть при тюнинге основного.

## 4. Бэкенд (Node/NestJS) — обязательные правки

В точке входа приложения:

- **`trust proxy` = loopback** — доверять прокси-заголовкам только от nginx.
- **helmet** — security-заголовки для API. CSP и HSTS в helmet отключить
  (CSP страниц и единый HSTS задаёт nginx), чтобы не конфликтовали.
- **compression** — сжатие JSON-ответов API (статику жмёт nginx).
- **disable x-powered-by** — не раскрывать, что это Express.
- **CORS — белый список доменов** из переменной окружения, НЕ `origin: '*'`
  (с `credentials: true` звёздочка небезопасна и не работает в браузере).

## 5. Применение и проверка

1. Правки вносить в `/etc/nginx/sites-available/<файл>` (в
   `sites-enabled/` обычно лежит симлинк на него). Обновить снимок в
   `deploy/nginx/` в репозитории.
2. `sudo nginx -t` — проверка синтаксиса. **Если ошибка — reload не
   делать**: работающий nginx продолжит жить на старом конфиге.
3. `sudo systemctl reload nginx` — применение без разрыва соединений.
   Если правка «не применилась» — проверить, что nginx её вообще видит
   (`nginx -T | grep <директива>`), и повторить прямым `nginx -s reload`:
   systemctl-reload изредка не подхватывает новые файлы conf.d.
4. Проверить curl'ом (чек-лист ниже) — по реальным URL, а не «на глаз».
   Ожидаемые значения сверять точно: сегодня «те же самые» заголовки с
   другим значением (`preload`, `DENY` вместо ожидаемых) выдали, что их
   ставит приложение, а не nginx.
5. Чек-лист автоматизировать скриптом и гонять после КАЖДОЙ правки —
   ручной список рано или поздно перестают выполнять. Готовый пример под
   текущий проект: `deploy/nginx/check.sh` (домены/пути — в переменных
   сверху, адаптируется за минуту). Запуск на сервере:
   `bash deploy/nginx/check.sh` — выход ненулевой при любом провале.

### Чек-лист проверки (curl)

| Что проверяем | Команда (суть) | Ожидаемо |
|---|---|---|
| Сжатие JS | запрос JS-чанка с `Accept-Encoding: gzip` | `Content-Encoding: gzip` |
| Сжатие API | запрос `/api/*` с `Accept-Encoding: gzip` | `Content-Encoding: gzip` |
| HTTP/2 | `curl -sI --http2 https://<DOMAIN>/` | `HTTP/2 200` |
| Статика с диска | заголовки ассета | `Cache-Control: ...immutable`, не 403/404 |
| Security фронт | заголовки главной | HSTS, X-Frame-Options, nosniff — по **одному** каждого (`grep -c`), без дублей |
| Security админка | заголовки админки | те же + X-Frame-Options: DENY, тоже без дублей |
| Версия скрыта | любой ответ | `Server: nginx` без номера версии |
| X-Powered-By убран | заголовки `/api/*` | заголовка нет |
| Лимит тела | POST крупного файла | не 413 в пределах лимита |
| Редирект HTTP→HTTPS | запрос по http | `301` на https |

## 6. Сертификаты (certbot)

Причина №1 внезапно лёгших «стабильных» сайтов — истёкший сертификат при
сломанном автопродлении. Let's Encrypt живёт 90 дней; продление обязано
работать без человека. Проверять при настройке и затем раз в квартал:

```bash
systemctl list-timers | grep certbot   # таймер существует и срабатывает
certbot renew --dry-run                # репетиция продления ВСЕХ сертификатов
```

Ожидаемо: таймер с недавним `last run`, dry-run завершается
`Congratulations, all simulated renewals succeeded`. Если dry-run падает —
чинить сейчас, а не когда сайт ляжет: типовые причины — порт 80 занят не
nginx'ом, домен больше не указывает на этот сервер, изменённый
webroot/конфиг renewal.

Certbot с nginx-плагином перезагружает nginx после продления сам. Срок
текущего сертификата снаружи: `echo | openssl s_client -servername <DOMAIN>
-connect <DOMAIN>:443 2>/dev/null | openssl x509 -noout -enddate` — эта же
проверка встроена в `check.sh` (алерт при < 20 днях).

## Частые ошибки

- **Сжатие «не работает».** HTML жмётся, а JS нет → `gzip_types` не задан
  (стоковый закомментирован). Добавить список типов. И проверить, что gzip
  включён для ВСЕХ доменов, а не только основного — блок админки забывают.
- **HTTP/2 «не включается» / "unknown directive http2".** Зависит от
  версии: 1.25.1+ — `http2 on;`; 1.24 и раньше — суффикс
  `listen 443 ssl http2;`. Проверять `nginx -v`. curl без `--http2`
  покажет HTTP/1.1 даже когда h2 работает — тестировать с флагом.
- **403 на статике при верном конфиге.** `alias` указывает в
  `/home/<user>/...`, а воркеры nginx работают под `www-data`, у которого
  нет прохода по цепочке каталогов. `nginx -t` при этом проходит — ошибка
  видна только на живом запросе. Лечится execute-битом на каждый каталог
  пути: `chmod o+x /home/<user> /home/<user>/... ` (содержимое домашки при
  этом не читается — только проход). Проверка:
  `sudo -u www-data ls <путь>`.
- **404 на всю статику.** Завершающие слэши `location /prefix/` и
  `alias /path/` не совпадают — путь склеивается неверно. Слэш либо в
  обоих, либо ни в одном.
- **413 на загрузке файлов.** Дефолтный `client_max_body_size` = 1 МБ.
  Поднять в server-блоке.
- **Keepalive «включён», но соединения не переиспользуются.**
  `proxy_http_version 1.1` + `Connection ""` без `upstream { keepalive N; }`
  не работают — нужен именно upstream-блок (Принципы п.4).
- **Rate-limit отдаёт 503.** Дефолт `limit_req` — 503, мониторинг видит
  «сервер упал». Ставить `limit_req_status 429;`.
- **`gzip`/`server_tokens`/`types_hash` duplicate.** Стоковый nginx.conf
  уже их содержит — в своём tuning-файле НЕ повторять `gzip on;` (только
  `gzip_types` и параметры).
- **Двойной Cache-Control на статике.** `expires 1y;` и `add_header
  Cache-Control` ставят заголовок каждый — использовать что-то одно:
  `add_header Cache-Control "public, max-age=31536000, immutable";`
  (и max-age, и immutable в одном заголовке), `expires` убрать.
- **Дубли security-заголовков с разными значениями.** nginx добавил
  `X-Frame-Options SAMEORIGIN`, а приложение уже шлёт `DENY` → клиент
  получает оба, поведение браузеров непредсказуемо. Перед добавлением
  заголовков в nginx проверить ответ самого Node-процесса
  (`curl -sI http://localhost:<PORT>/`) — см. Принципы п.6.
- **Правка «не применилась» после systemctl reload.** Новый файл в
  conf.d изредка не подхватывается systemctl-reload'ом. Диагностика:
  `nginx -T | grep <директива>` (показывает конфиг глазами nginx);
  лечение: прямой `nginx -s reload`.
- **Пропали security-заголовки в конкретном location.** Любой `add_header`
  внутри `location` отменяет наследование серверных `add_header`.
  Дублировать в этом location.
- **Двойные заголовки на API.** Если и nginx, и helmet ставят один
  заголовок → выбрать один источник (для API — helmet).
- **Порт в конфиге не тот.** Локальный `.env` может отличаться от
  серверного. Источник истины — фактический порт процесса на сервере
  (pm2/серверный .env).
