# Изображения: сжатие и хранение

Все фото, которые загружаются через API, перед сохранением в Yandex Object Storage
автоматически сжимаются на бэкенде. Загружать можно обычные jpg/png/webp.

## Две копии каждого фото

На каждое фото в хранилище кладутся два файла с общим именем и суффиксом `-opt`:

- `<имя>-opt.avif` — основная копия, AVIF качества 85;
- `<имя>-opt.jpg` — запасная копия для браузеров без AVIF (Safari на iOS 15 и старше), JPEG качества 85. Если у фото есть прозрачность, запасная копия — `<имя>-opt.webp` (WebP качества 90), потому что JPEG прозрачность не поддерживает.

В БД и в ответах API хранится ссылка на **запасную** копию. AVIF лежит рядом: тот же адрес, но с расширением `.avif`. Правило для фронтенда: если ссылка заканчивается на `-opt.jpg` или `-opt.webp`, у неё гарантированно есть AVIF-копия, и её нужно отдать браузеру первым вариантом (через `<picture>` с `type="image/avif"`). У ссылок без `-opt` (старые фото, если такие остались) AVIF-копии нет — их показывают как есть.

При удалении фото через API удаляются обе копии.

## Что происходит при загрузке

1. Фото поворачивается по EXIF-ориентации (снимки с телефона не ложатся набок).
2. Уменьшается по длинной стороне до лимита из таблицы ниже. Маленькие фото не растягиваются.
3. Удаляются метаданные (EXIF, в том числе GPS-координаты), цвета приводятся к sRGB.
4. Кодируется в AVIF и в запасной формат.
5. Обе копии загружаются с заголовком кэширования на год (`immutable`): у каждого файла уникальное имя, файл по имени никогда не меняется.

Если файл не удаётся прочитать как изображение, API отвечает 400.

| Где | Лимит по длинной стороне | Примерный вес AVIF / JPEG |
|---|---|---|
| Фото товара | 2000 px | 115–130 KB / 130–150 KB |
| Баннер, десктоп | 2560 px | ~160 KB / ~185 KB |
| Баннер, мобильный | 1440 px | меньше десктопного |
| Фото отзыва | 1600 px | — |
| Аватар | 512 px | — |

Исходные фото с камеры весят 5–7,5 MB, то есть экономия — в 40–60 раз.

AVIF кодируется в быстром режиме (effort 2): на сервере с одним ядром это около 1,5 секунды на фото вместо 8–12 секунд в медленном режиме, а вес больше всего на 5–10%. Загрузка 10 фото товара укладывается примерно в 15–20 секунд.

Как выбирали формат: на реальных фото товаров сравнивали JPEG, WebP и AVIF на разном качестве. WebP заметно размывает фактуру ткани даже на высоком качестве; AVIF и JPEG 85 сохраняют её близко к оригиналу. Выбрано AVIF 85 — по визуальному сравнению вариантов 45–85.

Лимиты на размер исходного файла (10 MB для товаров, 20 MB для баннеров, 5 MB для отзывов и аватаров) не изменились — это лимит на то, что принимает сервер, а не на то, что хранится.

## Уже загруженные фото

Для фото, загруженных до включения сжатия, в корне репозитория есть скрипт `optimize_existing_images.ts`. Запускать на сервере (нужен доступ к продакшн-БД и ключи S3 из `.env`):

- без флагов — пробный прогон: скачивает и сжимает фото, показывает экономию, ничего не меняет;
- `--apply` — загружает обе копии рядом с оригиналом и переписывает ссылки в БД (товары, баннеры, отзывы, аватары);
- `--rebuild` (вместе с `--apply`) — пересобрать AVIF и у фото, где он уже есть, например после смены качества.

Команда запуска: `npx ts-node --transpile-only optimize_existing_images.ts`, затем то же с `--apply`.

Скрипт можно запускать повторно: фото, у которых уже есть AVIF-копия, пропускаются. Фото, сжатые прошлыми версиями скрипта (есть `-opt`, но нет AVIF), пережимаются из оригинала — того же ключа без `-opt`, если он ещё лежит в хранилище, — чтобы не сжимать с потерями дважды. Несжатые фото, которые после сжатия стали меньше всего на 10% или меньше, остаются как есть.

В режиме `--apply` каждое изменение ссылки записывается в файл `optimize_images_backup_<время>.jsonl` (таблица, id, поле, старое и новое значение) ещё до записи в БД — по нему можно вернуть старые ссылки. Файл в git не попадает.

Оригиналы в S3 не удаляются — их можно удалить вручную, когда сайт проверен.
