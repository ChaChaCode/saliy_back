# Изображения: сжатие и хранение

Все фото, которые загружаются через API, перед сохранением в Yandex Object Storage
автоматически сжимаются на бэкенде. Фронтенду и админке ничего делать не нужно:
загружать можно обычные jpg/png/webp, в ответе и в БД будет ссылка на сжатый файл
(`.jpg` для фото товаров, `.webp` для остального).

## Что происходит при загрузке

1. Фото поворачивается по EXIF-ориентации (снимки с телефона не ложатся набок).
2. Уменьшается по длинной стороне до лимита из таблицы ниже. Маленькие фото не растягиваются.
3. Удаляются метаданные (EXIF, в том числе GPS-координаты), цвета приводятся к sRGB.
4. Сохраняется в формате из таблицы.
5. Загружается с заголовком кэширования на год (`immutable`): у каждого файла уникальное имя, файл по имени никогда не меняется.

Если файл не удаётся прочитать как изображение, API отвечает 400.

| Где | Лимит по длинной стороне | Формат и качество |
|---|---|---|
| Фото товара | 2000 px | JPEG (mozjpeg), 85 |
| Баннер, десктоп | 2560 px | WebP, 82 |
| Баннер, мобильный | 1440 px | WebP, 82 |
| Фото отзыва | 1600 px | WebP, 80 |
| Аватар | 512 px | WebP, 80 |

Почему товары в JPEG, а не в WebP: при сравнении на реальном фото джинсовки WebP даже на качестве 90–92 заметно размывает фактуру ткани и строчку, а JPEG при том же весе (около 150 KB вместо исходных 5–7 MB) сохраняет их почти как в оригинале. AVIF весит меньше всех, но размывает ещё сильнее и кодируется в разы дольше. Если у фото товара есть настоящая прозрачность, оно сохраняется в WebP (качество 90) — JPEG прозрачность не поддерживает.

Лимиты на размер исходного файла (10 MB для товаров, 20 MB для баннеров, 5 MB для отзывов и аватаров) не изменились — это лимит на то, что принимает сервер, а не на то, что хранится.

## Уже загруженные фото

Для фото, загруженных до включения сжатия, в корне репозитория есть скрипт `optimize_existing_images.ts`. Запускать на сервере (нужен доступ к продакшн-БД и ключи S3 из `.env`):

- без флагов — пробный прогон: скачивает и сжимает фото, показывает экономию, ничего не меняет;
- с флагом `--apply` — загружает сжатую копию рядом с оригиналом (`<имя>-opt.jpg` или `<имя>-opt.webp`) и переписывает ссылки в БД (товары, баннеры, отзывы, аватары).

Команда запуска: `npx ts-node --transpile-only optimize_existing_images.ts`, затем то же с `--apply`.

Скрипт можно запускать повторно: файлы с суффиксом `-opt` (результат прошлого запуска) пропускаются. Фото, которые после сжатия стали меньше всего на 10% или меньше, остаются как есть — повторное сжатие с потерями того не стоит.

В режиме `--apply` каждое изменение ссылки записывается в файл `optimize_images_backup_<время>.jsonl` (таблица, id, поле, старое и новое значение) ещё до записи в БД — по нему можно вернуть старые ссылки. Файл в git не попадает.

Оригиналы в S3 не удаляются — их можно удалить вручную, когда сайт проверен.
